# 발표 데모 배포 — Cloudflare Tunnel

> 목적: 발표 중 **공개 HTTPS URL로 접속해** 대시보드를 시연한다.
> 방식: 앱은 **노트북에서 그대로 돌고**, 터널이 그 앞에 공개 주소를 붙인다.
> 이 방식을 고른 이유: 발표장 인터넷이 죽어도 **URL만 버리고 `localhost`로 데모를 이어갈 수 있다.**
> 클라우드 VM에 올렸다면 그 경우 폴백이 없다.

---

## 0. 구조 — 무엇이 바뀌는가

로컬 개발에서는 브라우저가 백엔드(8000)를 **직접** 부른다. 데모 배포에서는 그 경로를 끊고
프론트(3000) 뒤로 넣는다.

```
[로컬 개발]   브라우저 ──┬─→ :3000 (화면)
                        └─→ :8000 (API 직접)          ← CORS 설정이 필요한 이유

[데모 배포]   브라우저 ──→ 터널 ──→ :3000 ──→ :8000
                                    │         (컨테이너 네트워크, 인터넷에 노출 안 됨)
                                    └ proxy.ts 비밀번호 한 겹 (화면·API 모두)
```

얻는 것 넷:

- 공개 URL이 **하나**로 준다(둘을 뚫고 CORS를 맞추는 일이 없다).
- same-origin이라 **CORS 설정을 안 건드린다**(HANDOFF §2의 `Load failed` 함정을 피한다).
- 백엔드가 인터넷에 노출되지 않아 **비밀번호를 우회할 길이 없다.**
- SSE도 same-origin이라 브라우저가 인증 헤더를 자동으로 붙인다(`EventSource`는 헤더를
  직접 못 싣는다 — 이 구조라서 되는 것이다).

**손댄 파일 넷** (대시보드 화면 코드는 건드리지 않았다):

| 파일 | 무엇 |
|---|---|
| `frontend/next.config.ts` | `/api/*` → 백엔드 rewrites. **로컬 개발은 이 경로를 타지 않는다** |
| `frontend/src/proxy.ts` | 비밀번호 한 겹. ⚠️ Next 16에서 `middleware`→`proxy`로 이름이 바뀌었다 |
| `docker-compose.demo.yml` | 겹쳐쓰기: 상대경로 · 비밀번호 · 프로덕션 빌드 |
| `docs/DEMO-DEPLOY.md` | 이 문서 |

## 1. 준비 (발표 전날)

### 비밀번호 정하기

`.env`에 두 줄 넣는다. **영숫자만** 쓴다(Basic 인증이 한글·특수문자에서 깨질 수 있다).

```
DEMO_USER=pb
DEMO_PASSWORD=<정해서 넣기>
```

⚠️ `DEMO_PASSWORD`가 없으면 프론트 컨테이너가 **아예 안 뜬다** — 비밀번호 없이 공개되는
사고를 막으려고 일부러 그렇게 뒀다.

### cloudflared 설치 (이미 됨)

```
brew install cloudflared
```

### 데모 데이터 채워 두기

발표 중에 F3를 라이브로 돌리지 않는다(~100초). HANDOFF §0 표대로 미리 채운다.
**상태가 골고루 있어야** 큐와 통과율이 의미를 갖는다(초안·검토중·심의중·발행완료 각 1건 이상).

---

## 2. 발표 당일 아침 — 띄우기

### ① 앱을 데모 모드로 올린다 (빌드 1~3분)

```
cd <레포>
docker compose -f docker-compose.yml -f docker-compose.demo.yml up -d --force-recreate frontend
```

빌드가 끝났는지:

```
docker compose logs --tail=20 frontend      # "Ready in" 이 보이면 됨
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/dashboard   # 401 이면 정상
curl -s -o /dev/null -w '%{http_code}\n' -u pb:<비밀번호> http://localhost:3000/dashboard  # 200
```

**401이 나와야 정상이다** — 비밀번호가 걸렸다는 뜻이다.

### ② 터널을 뚫는다

```
cloudflared tunnel --url http://localhost:3000
```

출력에 `https://<랜덤한-이름>.trycloudflare.com` 이 뜬다. **이 창을 닫지 마라** — 닫으면 URL이 죽는다.

⚠️ **8000에는 터널을 뚫지 않는다.** 뚫으면 비밀번호를 우회하는 경로가 생긴다.

### ③ 브라우저에서 한 번 로그인해 둔다

발표 시작 전에 그 URL을 열고 `pb` / 비밀번호를 입력해 둔다. 그러면 시연 중에
로그인 창이 뜨지 않는다. **탭을 미리 열어 두고 발표에 들어간다.**

---

## 3. 발표 중

- 준비된 탭으로 시연한다. URL을 화면에 보여줄 일이 있으면 주소창을 그대로 쓴다.
- **라이브 실행은 F1 질문(수 초)까지만.** F3(~100초)·F2(40~50초)는 미리 만든 결과로 보여준다.
- 인터넷이 죽으면 **`http://localhost:3000`으로 갈아탄다** — 앱은 노트북에서 도는 그대로다.
  (터널만 죽은 것이므로 데모는 계속된다. 이게 이 방식을 고른 이유다.)

---

## 4. 발표 후 — 되돌리기

터널 창에서 `Ctrl+C`. 그러면 URL이 즉시 죽는다.

개발 모드로 복귀:

```
docker compose up -d --force-recreate frontend
```

(겹쳐쓰기 파일을 안 주면 기본 compose로 돌아간다 — dev 서버 · 백엔드 직접 호출.)

---

## 5. 함정 — 긴 요청이 30초에 끊긴다 (해결됨, 되돌리지 말 것)

⚠️ **Next의 rewrites 프록시는 기본 타임아웃이 30초**다
(`next/dist/server/lib/router-utils/proxy-request.js`의 `proxyTimeout || 30000`).
이 앱의 긴 요청은 그보다 오래 걸린다 — **브리핑 40~50초 · F3 노트 ~100초.**

실제로 이렇게 나타났다: 브리핑 버튼을 누르면 화면에 **"브리핑 생성에 실패했습니다"**(500)가
뜨는데, **백엔드는 성공해서 DB에 저장했다.** 프록시가 완료 5~10초 전에 연결을 끊은 것이고,
프론트 로그에는 `Failed to proxy … socket hang up (ECONNRESET)`만 남는다.
**크레딧은 이미 나간 뒤**라 실패로 보이는 쪽이 더 나쁘다.

해결: `frontend/next.config.ts`의 `experimental.proxyTimeout: 300_000`.

- ⚠️ 이 키는 **공식 문서에 없다**(config 스키마에만 있다). Next를 올릴 때 살아 있는지 확인할 것 —
  조용히 무시되면 증상이 그대로 돌아온다. 확인법:
  `docker compose exec -T frontend sh -c "grep -o '\"proxyTimeout\":[^,}]*' .next/required-server-files.json"`
- **터널 쪽은 범인이 아니다.** 실측으로 Cloudflare 퀵 터널은 **최소 120초까지 통과**했다
  (30·60·100·120초 지연 응답 전부 200). 끊은 것은 Next 프록시였다.
  → F3(~100초)도 터널을 통과한다. 그래도 발표 중 라이브 실행은 권하지 않는다(§3).
- 로컬 개발은 rewrites를 안 타므로 이 설정과 무관하다 — **데모 배포에서만 드러나는 함정이다.**

---

## 6. 알아 둘 것

- **퀵 터널 URL은 매번 바뀐다**(`trycloudflare.com`). 고정 주소가 필요하면 도메인을
  Cloudflare에 붙여 named tunnel을 써야 한다 — 발표 한 번이면 필요 없다.
- **비밀번호 한 겹은 데모용이다.** 실서비스 인증이 아니다. 발표에서 "인증은 어떻게 하나"를
  물으면 HANDOFF §7의 그 항목이 정직한 답이다 — **역할 강제가 아직 서버에 없다.**
- API 키는 컨테이너 환경변수로만 들어간다. 브라우저로는 나가지 않는다.
- 목업 고객 50명은 **가짜 데이터**다. 그래도 공개 URL에 올라가는 것이니 노출 시간을
  발표 시간으로 줄이는 게 맞다(터널을 그때만 켜는 이유).
